# User Interface Internationalization (i18n) and Localization Rule

This document defines the mandatory architectural guidelines, workflows, and constraints for managing user interface internationalization (i18n) and localized strings across the WhatsNexus codebase.

---

## 1. Single Source of Truth (`src/locales/`)

1. **Dedicated Directory:** All user-facing strings, system labels, hints, modal dialog messages, button texts, accessibility labels, and tooltips must reside strictly and exclusively in individual JSON dictionaries located at `src/locales/<lang-code>.json`.
2. **Canonical Reference:** `src/locales/en.json` serves as the primary ground truth and authoritative template for all localization keys.
3. **No Alternative Stores:** Texts must never be imported, consumed, or parsed from arbitrary external APIs, secondary files, or inline dictionary literals inside renderer scripts. The IPC handler `load-locale` in `src/main.js` and `fetchLocaleJson()` in `src/renderer/renderer.js` strictly resolve to `src/locales/`.

---

## 2. Strict Zero-Hardcoding Policy

1. **HTML Templates (`index.html`, etc.):**
   - **No Plain Hardcoded Strings:** No user-visible text may be written directly inside HTML markup.
   - **Text Elements:** Must declare the `data-i18n="<key>"` attribute on the element (e.g. `<h3 data-i18n="welcome"></h3>`).
   - **Input Placeholders:** Must declare `data-i18n="<key>"` or `data-i18n-placeholder="<key>"`.
   - **Title Tooltips:** Must declare `data-i18n-title="<key>"` (e.g. `<button data-i18n-title="view_gpl_license_title">`).
   - **Accessibility Labels:** Must declare `data-i18n-aria="<key>"` (e.g. `<button data-i18n-aria="btn_close">`).
2. **JavaScript Scripts (`renderer.js`, etc.):**
   - Whenever dynamic text is created, rendered, or updated (via DOM APIs or notifications), strings must be extracted from the active dictionary (`currentTranslations[key]` or `i18n[settings.language][key]`).
   - Any fallback argument supplied in code (e.g., `getTranslation(key, fallback)`) must strictly be written in neutral English.
3. **CSS Stylesheets (`style.css`, etc.):**
   - Pseudo-elements (`::before`, `::after`) must never inject visible language-dependent words via the CSS `content:` property. The `content` property is strictly reserved for empty layout spacers, glyphs, or decorative indicators (`content: ''`).

---

## 3. Mandatory 100% Key Parity Across All Locales

1. **Symmetric Dictionary Parity:** Whenever a new key is added or modified in `en.json`, it is mandatory that the identical key is synchronized across **every single supported `.json` file** in `src/locales/`.
2. **No Orphaned Keys:** A build or release will be considered broken if any language dictionary lacks keys present in `en.json`. If a native translation is not yet established, the English canonical value must be populated as the default placeholder.

---

## 4. Language Registration Protocol

To introduce a new language or constructed language (conlang):
1. **JSON Provisioning:** Add `src/locales/<langCode>.json` containing the complete 100% synchronized key suite.
2. **Renderer Registration:**
   - Register the language identifier code in the `supportedLanguages` array in `src/renderer/renderer.js`.
   - Register the native name in the `nativeNames` dictionary in `src/renderer/renderer.js` to ensure proper presentation in the Settings language selector.
3. **Dynamic Attribute Synchronization:**
   - The application must always set and update `data-language` and `lang` on `document.documentElement` (`<html data-language="..." lang="...">`) to allow custom font stacks (such as Tengwar or Klingon pIqaD) and RTL styles (such as Arabic or Urdu) to activate reactively.
4. **Spellchecker Integration:**
   - When applicable, verify native Chromium BCP-47 identifier mappings in `src/main.js` (`SPELLCHECK_MAP`) for session-level spellcheck support.
